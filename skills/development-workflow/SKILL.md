# 开发流程总入口

先读项目约定、Git 状态与受影响文件，识别用户要讨论、方案、实施、调试还是归档。已有流程和明确授权优先，不把普通小修改扩展成完整规格工作流。

## 任务分派

| 当前目标 | 选择 |
|---|---|
| 明确采用 OpenSpec，仍在探讨问题 | `openspec-explore`，保持探索范围 |
| 明确采用 OpenSpec，需要一次形成方案与任务 | `openspec-propose` |
| 实施/继续已有 OpenSpec 变更 | `openspec-apply-change` |
| 将增量规格合入主规格，暂不归档 | `openspec-sync-specs` |
| 完成已有变更并归档 | `openspec-archive-change` |
| 有明确报错或错误结果 | 使用本入口的最小调试流程，不额外加载独立调试技能 |
| 用户选择 TDD、先写测试或红绿重构 | `tdd` |
| 明确维护 AI 项目约定/AGENTS.md | `project-context-maintainer` |
| 希望质询方案并对齐术语与领域决策 | `grill-with-docs` |
| 已选 Swift，处理语言或并发问题 | `write-swift` |

需要具体输入、资源和限制时读取 [专长目录](references/specialists.md)。小型普通改动可直接按项目规范完成；`karpathy-guidelines` 是实现约束参考，不是必须追加的独立阶段。界面任务可交给现有 `ui-design`，不在本入口再选一套视觉规范。

## 工作流边界

选中后读取专长完整入口及相关资源。OpenSpec 命令依赖已安装 CLI 和项目配置；使用其返回的 planningHome、changeRoot、actionContext、allowedEditRoots，不硬编码变更目录。工作区只允许规划时不越界实施。

只要修一个错误，不强制建立 OpenSpec；只要求讨论，不执行实施或归档；单纯同步规格，不自动归档。保持用户已给出的变更名和流程选择，只有真实歧义才提问，不机械重复审批。

## 最小调试流程

先保留可复现输入与关键错误，定位失败位置及运行环境，再做最小修改并运行相关检查。需要缩短长日志时保留原因链和关键上下文，不固定只取末尾或最后一帧。连续失败先检查假设、输入和环境，不按重试次数直接重写全部代码。

## 验证与交付

选择与变更相称的最小可运行检查，保留实际失败及修复证据。TDD 用行为测试逐项推进；调试报告保留关键错误和实际回归结果。缺工具或依赖时明确未验证，不能仅按 Skill 的静态分宣称代码成功。

不因代码实现自动推送、部署、归档用户资料或执行数据库破坏操作。执行这些动作时沿用本次任务的具体授权与项目约定。
