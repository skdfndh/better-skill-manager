# 使用记录与每周复盘

## 记录边界

这是 Agent 遵循全局指令执行的本地记录协议，不是宿主强制审计或聊天监听器。只统计已记录的实际使用；未记录不证明未使用。仅浏览技能目录、审查候选文件不算调用。总入口和实际采用的专长分别记录，沿用同一个任务标识；任务数去重，不能把总入口和三个专长说成四次独立任务。

从启用时开始记录，不编造过去使用次数或满意度。只保存简短任务类型、Agent、技能实际入口及 SHA-256、角色、产出状态与必要的脱敏反馈摘要，不存对话全文、产物正文或凭据。入口哈希不代表整包哈希，支撑资源发生变化时仍需重新核对版本。日志和真实周报留在用户本机，不放入公开仓库。

使用标准库脚本 `scripts/usage_log.py`，默认数据为 `~/.skill-shelf/usage/usage.sqlite3`。不需要运行管理器或 HTTP 服务；支持四个 Agent 共享 SQLite 事务写入。Python 不可用或被权限限制时如实说明漏记，恢复后只补有明确证据的记录。不要为记录绕过宿主权限或执行未知技能代码。

## 任务生命周期

执行 `python <skill-curator>/scripts/usage_log.py --help` 查看命令。推荐把输入写到本地临时 JSON，再执行 `record <input.json>`，避免命令行转义或暴露大段内容。测试使用 `--data-dir <隔离目录>`，不要把合成反馈写进真实库。PowerShell 可使用已验证的 Python 绝对路径；跨平台路径按实际环境填写。

实际采用技能后，先记录 start 并保存返回的 `usage_id`：

```json
{"kind":"start","task":"同一任务持续使用的唯一标识","agent":"codex","entry":"实际采用的 SKILL.md 绝对路径","role":"specialist","task_kind":"界面优化"}
```

agent 可选 `codex / claude-code / antigravity / dsh`；role 可选 `router / specialist / support`。同任务、Agent、实际入口、版本和角色重试会返回同一个 ID，解析目录联接后去重；内容变化保留为另一版本。不同任务须使用不同 task，单次任务的后续调整继续沿用原标识。

交付、失败或取消后追加 result，交付成功不能自动记满意：

```json
{"kind":"result","usage_id":"start返回的ID","event_key":"任务内唯一结果消息标识","outcome":"delivered","evidence":"产物已保存，相关检查通过；用户尚未评价"}
```

outcome 可选 `delivered / failed / cancelled / unknown`。收到后续用户反馈时关联明确的任务和技能，再追加 feedback：

```json
{"kind":"feedback","usage_id":"start返回的ID","event_key":"任务内唯一反馈消息标识","satisfaction":"unknown","revision":"major","source":"user_request","attribution":"requirements_change","evidence":"用户新增页面后要求大幅调整；没有明确评价上一产物"}
```

- satisfaction：`satisfied / mixed / dissatisfied / unknown`，只有用户明确评价才能使用前三项，source 必须为 `user_explicit`。沉默、“继续”或换需求不能推断满意程度。
- revision：`none / minor / major / unknown`，依据用户实际修改要求。改变主要目标、结构或重做主要产物属于 major；文字细调或局部修复属于 minor。要求大改不必然代表不满意；Agent 自检返工不能记成用户要求返工。
- source：`user_explicit / user_request / agent_observed`；后者仅记可观察事实，不能代替用户评价或修改要求。
- attribution：`skill / routing / environment / requirements_change / execution / unknown`；先区分技能缺陷、选错专长、环境缺依赖、需求变化、执行偏差。证据不够填 unknown，不强行归责。
- evidence：1–300 字的非敏感摘要，保留判断依据。来源及归因是人工填报，脚本不能验证其真实性。

event_key 用真实消息标识或本轮保存的稳定标识。相同键重复写入幂等，不同内容拒绝覆盖；修改判断应追加新键，保留历史。同一任务用了多个技能时，只将反馈记到有因果证据的技能，不能给全部专长批量扣分。可用 `recent --task <任务标识>` 找原 ID；关联不明时保留“未归因”待核对，不猜最近任务。

## 周日复盘

沿用用户现有周总结时间；先 `review` 生成带 review_id、事件区间和受影响任务的 JSON 摘要。开始生成不会消费记录；范围是上次成功复盘之后的事件至本次快照，跨周晚到反馈仍会纳入。新使用与既往使用的新反馈分开，不重复增加使用次数。没有数据时写“暂无记录/覆盖待验证”，不生成满意率或低频删除结论。

将报告保存为独立 Markdown 文件并包含 review_id；按技能、实际入口、版本列出已记录任务数、交付状态、明确满意/不满/未知、用户要求大改的任务及归因，引用必要证据。一次任务多次反馈不当作多个独立样本；展示反馈变化，未知不进入满意率分母，小样本直接列次数，不作排名。每个建议写明根因、动作、验证和恢复办法。

1. **保留或复评**：用使用事实补充 G 当前需求；用可复现缺陷补 Q，可靠可迁移内容补 D。满意度是证据之一，不机械转换为 Q/G/D 分数；跨版本不混算。未使用可能是没有需求、没被发现或记录缺失，不能据此自动删除。
2. **小幅修订**：用户已授权每周改进。对明确且可复现的局部问题，或多个独立任务重复同一根因，可先保存本地备份，再作最小说明修订并运行相关验证；保留来源与独立更新边界，核对四个 Agent 联接及管理器元数据。没有真实证据则只提建议，不能用一次新需求改掉通用规则。
3. **蒸馏、结构大改与删除**：给出具体对象、原版本、有效内容接收位置和验证结果。大范围重写、迁移、删除先呈现具体清单，由用户决定；删除须同时核验 R 五项和该清单的真实授权，优先回收站并清理真实联接。自动化提示或数据库字段均不授予删除权限；无回复不算同意。

报告保存且相关检查完成后执行 `commit-review <review_id> <周报.md>`。脚本核验报告非空、包含该 ID、当前游标没有被其他复盘推进后才确认；失败不推进，成功重试幂等。复盘期间新写入的事件留给下次。保存的文件哈希用于核对历史，不能证明报告内容或检查真实完成。

周总结补充报告位置、已完成的小修、待选择清单和未验证范围。没有重要变化时不要额外频繁提醒；不额外创建重复的周任务。全局规则只保证指令接入，不保证宿主每次均执行，首次实际使用后应检查各 Agent 的记录覆盖。
